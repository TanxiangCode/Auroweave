# 🚀 项目计划书：下一代极简跨平台代理客户端（代号：Auroweave）· v4

## 一、项目定位与核心哲学

作为专注于 Windows/macOS 的现代化代理客户端，Auroweave 拒绝做旧时代 Clash 的"皮肤壳子"，而是**从 Sing-box 底层特性出发**进行原生设计，专为开发者与重度网络极客打造。

- **极简至上（Minimalism）**：主界面常驻后台，95% 的高频盲操通过全局快捷搜索框完成。
- **绝对透明（Transparency）**：打破网络黑盒，让分流规则、DNS 解析、链路拓扑完全可视化。
- **本地安全（Privacy First）**：坚守隐私底线，订阅解构与规则合并 100% 在前端本地完成，杜绝凭证上传。

> **视觉哲学补充（v4 新增）**：本版本融合了一份独立设计的 UI/UX 方案（详见第七章），提出"空间感知 / 能量映射 / 渐进式呈现"三大视觉原则。其中"渐进式呈现"与本计划书此前已确立的产品决策——高级设置默认收起、拓扑画布默认隐藏——是同一件事的两个层面：前者讲"隐藏功能入口"，后者讲"隐藏视觉复杂度"，两者高度自洽，因此予以采纳并作为第七章的统领原则。

> **差异化验证前提**：正式开发前先实际体验 Clash Verge Rev、FlClash、Hiddify 等现有客户端，确保资源投入真正落在"独占优势"上。

## 二、完整技术栈方案

### 2.1 前端技术方案

- **核心框架**：Vue 3（Composition API，`<script setup>`）+ TypeScript + Vite 5+
- **样式方案**：Tailwind CSS + Shadcn Vue，颜色/圆角/间距全部通过 Design Tokens（CSS 变量）注入，禁止硬编码（详见 6.2、7.0）
- **拓扑图引擎**：@vue-flow/core
- **状态管理**：Pinia
- **图表库**：网速曲线、测速结果可视化（如 apexcharts/uPlot，注重轻量与实时刷新性能）
- **【新增】动效引擎**：优先使用浏览器原生 CSS Transition/Animation 实现常规过渡；能量核的流体动画使用 `conic-gradient` + `requestAnimationFrame` 或轻量 SVG 方案实现，不引入 three.js 等重型渲染库；设置面板的"胶囊变形转场"优先尝试 View Transitions API（Chromium/WebView2 支持较好，macOS WKWebView 支持情况需在模块 K 中预研），若兼容性或帧率不达标，退化为轻量动画库（如 motion-v）手写 FLIP 动画，而非死磕原生 API 拖慢整体进度

### 2.2 后端技术方案

- **核心外壳**：Tauri 2.0
- **系统进程与应用审计**：Rust `sysinfo` 库 + 平台原生 API
- **网络状态监听**：Rust 本地底层库，监听网卡切换及 Wi-Fi SSID 广播
- **全局热键捕获**：Tauri 2.0 全局快捷键插件

### 2.3 核心内嵌（Sidecar）逻辑

- 独立进程守护模式，Tauri 后台静默拉起 Sing-box 二进制文件
- 监听系统挂起（Sleep）与唤醒（Wake）信号，自动重连

### 2.4 权限与系统集成技术预研清单

| 功能 | 涉及权限/机制 | 需要验证的问题 |
|---|---|---|
| TUN 模式接管全局流量 | Windows 管理员权限；macOS 网络扩展 | 首次安装权限申请流程、UAC 弹窗时机 |
| 应用防火墙分流（App-Matrix） | macOS 辅助功能权限；Windows UWP 包名识别 | `sysinfo` 能否拿到完整应用路径；UWP 需专门 API |
| 全局热键 | macOS 辅助功能权限 | 与系统级快捷键冲突检测与规避 |
| 二进制自动更新 | 代码签名与校验 | 更新时如何校验来源 |
| 【新增】无边框窗口（Windowless） | Windows Snap Layout、macOS 原生红绿灯样式规范 | 自定义窗口按钮是否会丢失 Windows 11 Snap Layout 悬浮菜单；macOS 是否允许在红绿灯附近放置自定义控件而不违反 HIG |

**建议输出物**：《权限预研报告》，明确每项功能的最小权限申请路径与降级方案。

## 四、核心功能点与亮点设计矩阵

### 4.1 榨干 Sing-box 独占特性的模块

> **分类调整说明**：App-Matrix 与拓扑画布本质上都是**配置流量往哪走（Routing 配置）**——App-Matrix 是"给应用指定出口"，拓扑画布是"给流量指定路径（含多跳链路）"，只是复杂度不同。而 DNS 实况看板是**观察流量已经怎么走了**，属于监控/审计类。因此重新归类为两大类：
>
> - **分流配置类（Routing）**：App-Matrix + 拓扑画布，合并为统一的 Routing 页面，用"简单模式 / 高级模式"两个 Tab 区分复杂度（详见 7.4）
> - **审计监控类（Audit）**：DNS 实况看板，保留为纯只读的观察面板，v4 中进一步升级为"语义化安全看板"（详见 7.5）

1. **分流配置（Routing）—— 简单模式：应用防火墙分流（App-Matrix）**：读取活动进程列表，以列表形式为应用绑定出站节点，面向日常需求
2. **分流配置（Routing）—— 高级模式：拖拽式"拓扑画布"链式代理（Node ChainingCanvas）**：Vue Flow 画布连线生成 `dialer` 嵌套 JSON，面向多跳链路的重度极客需求

   > **优先级说明**：高级模式（拓扑画布）默认收起在 Routing 页面的"高级模式"Tab 后面，不强制所有用户接触；是否显示由 Settings → 高级设置中的"启用拓扑图功能"开关控制（默认关闭）。开发优先级依然低于简单模式。

3. **审计监控（Audit）：DNS 泄露与解析路径实况看板（DNS Tracker）**：请求域名 ➡️ 路由规则 ➡️ DNS 出站 ➡️ 响应 IP，纯只读展示，v4 中新增"语义化翻译"呈现层（详见 7.5），本质仍是只读，不提供任何修改入口

### 4.2 智能测速与负载均衡模块（对标 Hiddify）

#### 4.2.1 延迟测速（Latency Test）
- 底层：Sing-box 原生 `urltest` 出站，配置统一测速 URL、间隔（interval）、容差（tolerance）
- UI：分组卡片显示"自动"标签 + 当前生效节点 + 延迟数值；提供"立即测速"批量按钮

#### 4.2.2 负载均衡出站（Load Balance）
- 底层：对接 Sing-box 负载均衡出站
- ⚠️ 需锁定明确 sing-box 版本并做兼容性回归测试（社区已有反馈部分版本 balancer 策略格式不兼容）
- UI：默认关闭，开启前提示 IP 跳变风险

#### 4.2.3 节点网速测试（上传/下载速度 + 延迟）

延迟测速只能反映"连接是否通畅、往返时间多长"，无法反映真实可用带宽，因此单独设计一套**吞吐量测速**能力。

**测试类型分级**（避免对所有节点做重型测速导致带宽浪费和体验卡顿）：

| 类型 | 说明 | 触发方式 | 数据消耗 |
|---|---|---|---|
| 延迟测速（Ping Test） | 复用 4.2.1 的 `urltest` 机制 | 自动周期性 + 手动批量 | 极低（几 KB） |
| 单节点网速测试（Speed Test） | 对**单个**选中节点做下载 + 上传吞吐量测试 | 用户手动点击某节点的"测速"按钮 | 中等（默认测试包 5-20MB 可配置） |
| 批量网速测试（Batch Speed Test） | 对当前分组内所有节点依次做吞吐量测试（串行，避免抢占带宽互相干扰） | 用户主动触发，需二次确认 | 较高，需明确提示预计耗时与流量消耗 |

**技术实现要点**：
- **下载测速**：通过对应节点的出站代理，向预设测速服务器发起分块下载请求，限定测试时长（如 5-8 秒）或限定数据量，计算平均速率
- **上传测速**：同理，向测速服务器上传固定大小的随机数据块，计算平均速率
- **测速服务器可配置**：在设置页提供默认测速地址，同时允许用户自定义
- **测速期间的干扰规避**：批量测速时需在 Rust 后台做串行调度，同一时刻只测一个节点
- **结果展示**：节点卡片增加"下载 ↓ / 上传 ↑ / 延迟"三项数值展示，支持按下载速度排序；历史测速结果做本地缓存

**UI 设计**：
- 节点列表每行右侧提供"⚡延迟"和"📶测速"两个独立按钮，避免用户误触发重型测速
- 测速中的节点卡片显示进度动画（详见 7.3，与能量映射视觉语言统一）
- 批量测速前弹出确认框，说明"预计耗时 X 秒，将消耗约 X MB 流量"

#### 4.2.4 一键订阅自动分组（Auto Group by Region）
- 解析订阅节点名称/地区标记，自动分组并生成 `urltest` 自动测速出站
- 导入订阅时提供"自动整理分组"开关，默认开启

#### 4.2.5 策略组快速切换
- Spotlight 命令框支持"分组名 + 模式关键字"一键切换（如"香港 自动"）

### 4.3 效率至上：开发者创新模块

1. **Spotlight 快捷搜索框（Command Palette）**
2. **开发者一键环境配置（Developer Toolkit）**
3. **场景自动化引擎（Ambient Network Automation）**

### 4.4 用户体验（UX）极致打磨模块

1. **本地离线订阅转换与规则合并引擎**（数据流：前端解析节点 + 文本层规则合并 → Rust 调用 sing-box 编译生成 `.srs` + config.json，全程无凭证上传）
2. **桌面端原生托盘与菜单栏生态**

## 六、代码开发规范

### 6.1 通用原则

- **单一职责**：一个函数/组件只做一件事；Rust 命令函数、Vue 组件都不应超过 300 行，超过则拆分
- **类型先行**：前后端数据结构先在 `src/types/` 中定义 TS 接口，Rust 端使用 `serde` 对应的 struct 保持字段命名与类型一致
- **禁止魔法值**：端口号、超时时间、测速数据包大小等常量统一放入 `constants.ts` / `constants.rs`

### 6.2 前端规范（Vue 3 + TypeScript）

- **组件写法**：统一使用 `<script setup lang="ts">`，禁止 Options API
- **命名约定**：组件文件名 PascalCase；组合式函数 `use` 前缀 + camelCase；Pinia store `xxx.store.ts`
- **TypeScript**：开启 `strict` 模式，禁止使用 `any`
- **样式**：仅使用 Tailwind 原子类 + Design Tokens CSS 变量（`tokens.css`），**禁止在组件内硬编码颜色值、圆角值、阴影值**——即便是设计稿里给出的具体色号，也必须先落到 tokens 里再引用
- **【新增】动效实现规范**：任何非功能必需的装饰性动画（流体波动、粒子背光、卡片变形转场等）必须通过 `useReducedMotion()` 判断后再决定是否播放完整效果；判断逻辑需同时兼容系统级 `prefers-reduced-motion` 与软件内"性能模式"开关，两者任一开启即降级
- **状态管理边界**：跨组件共享的状态放 Pinia；仅组件内部使用的状态用 `ref`/`reactive`
- **IPC 调用**：禁止在组件内直接调用 `invoke()`，必须通过 `src/api/ipc/` 封装层调用
- **Lint 工具**：ESLint（Vue 官方推荐规则集）+ Prettier，提交前自动格式化

### 6.3 后端规范（Rust）

- **格式化与静态检查**：强制使用 `rustfmt` 格式化，`clippy` 检查需在 CI 中设为阻断项
- **错误处理**：禁止 `unwrap()` / `expect()` 用于可能失败的业务逻辑，统一使用 `Result<T, AppError>`
- **模块边界**：`commands/` 层只做参数校验与调用编排，具体逻辑下沉到 `core/`、`speedtest/` 等领域模块
- **异步规范**：I/O 密集型操作一律使用 `tokio` 异步
- **日志规范**：使用 `tracing` 库，按模块设置 target，禁止使用 `println!`

### 6.4 IPC 与通信规范

- **命令命名**：`模块_动作` 格式，如 `speedtest_run_single`、`subscription_import`
- **返回结构统一**：所有 IPC 命令返回统一的 `ApiResponse<T>` 结构
- **WebSocket 数据**：高频数据走 WebSocket，低频操作走 IPC Command

### 6.5 Git 工作流规范

- **分支模型**：`main` / `develop` / `feature/*` / `fix/*`
- **提交信息**：遵循 Conventional Commits 规范
- **PR 要求**：涉及核心逻辑的改动必须附带对应测试用例才能合并
- **代码评审清单**：是否有硬编码常量、是否有裸露的 `unwrap()`、动效代码是否接入 `useReducedMotion()`

### 6.6 AI 辅助开发专项约定

- 每次让 AI 生成涉及 IPC 边界的代码时，先明确双方的数据结构再生成实现
- AI 生成的核心解析/测速/规则合并逻辑，要求同步生成对应单元测试
- 涉及权限、系统 API、窗口原生样式（如 macOS 红绿灯）的代码，生成后必须在真实设备上验证一次，不能默认 AI 给出的平台 API 调用一定准确——这类 API 在文档与实际行为上经常有细微差异

## 七、视觉设计系统与 GUI 布局设计（v4：融合 UI/UX 设计方案）

> 本章融合了一份独立设计的《Sing-box GUI 客户端全景 UI/UX 设计方案说明书 V2.0》。原方案的美术水准和交互创意很有亮点，尤其是"能量映射"的可视化思路和"渐进式呈现"的信息架构，与本计划书既有的产品决策高度契合。但原方案作为纯粹的视觉说明书，没有考虑跨平台工程实现的具体约束，本章在采纳其设计语言的同时，对每个高复杂度模块都补充了**工程可行性说明与降级方案**，避免团队在开发中为了还原设计稿而在次要细节上过度投入。

### 7.0 设计哲学与设计资产（Design Tokens）

三大视觉原则，与产品哲学（第一章）呼应：

- **空间感知（Spatial Awareness）**：功能模块视为视窗内的实体卡片，通过原地形变与缩放转场，减少"白屏切页"的割裂感
- **能量映射（Energy Mapping）**：网络数据可视化为流体速度与光效强弱，而非纯文本数字
- **渐进式呈现（Progressive Disclosure）**：界面默认极简，高阶功能（拓扑画布、原始日志、自定义 JSON 注入）隐匿于次级交互中——这与第四章"高级模式默认锁定""高级设置默认收起"的产品决策完全一致

**色彩体系（深色主题）**：

| Token | 取值 | 用途 |
|---|---|---|
| `--layer-0` | `#0B0B0C` | 视窗底色 |
| `--layer-1` | `#18181B` @ 40% + `blur(20px)` | 磨砂玻璃面板 |
| `--accent-blue` | `#007AFF` | 主强调色 |
| `--accent-cyan` | `#22D3EE` | 全息高亮（流体、进度动画） |
| `--accent-red` | `#EF4444` | 警告 |

**⚠️ 优化建议 1：补全浅色主题 Token**
原方案只给出了深色赛博风格的配色，但本计划书此前的设置项清单中已经明确了"外观主题：浅色 / 深色 / 跟随系统"三选项。浅色模式不能靠简单调亮深色 Token 敷衍了事（那样磨砂玻璃、全息发光在浅底上大概率不成立），需要单独设计一套浅色下的 `--layer-0` / `--layer-1` / 强调色，并在视觉上验证磨砂玻璃效果在浅色背景下是否依然成立，否则可能需要为浅色主题单独简化掉部分毛玻璃/发光效果。

**⚠️ 优化建议 2：对比度检查**
全息强调色（尤其警告红 `#EF4444`）在 40% 透明度的磨砂玻璃面板上，文字对比度可能达不到 WCAG AA 标准（4.5:1），需要在设计定稿前用对比度工具实测，而不是仅凭视觉观感判断。

**几何与字体**：iOS 级超椭圆圆角（主卡片 16-24px，小组件 7-10px）；西文 SF Pro Display/Inter，中文 PingFang SC，严格基线对齐。

### 7.1 视窗全局架构：无边框窗口 + 控制胶囊 + 能量核首页

```
┌───────────────────────────────────────────────────────────┐
│                                           [ ⚙️ │ ─  ⬜  ✕ ] │ ← 全局控制胶囊
│                                                           │
│                        ( 🟢 运行中 )                       │
│                      /   ⚡ 2.4 MB/s \                    │
│                     |     [ 连 接 ]   |   ←── 中央能量核    │
│                      \   📈 28 ms    /                    │
│                                                           │
│    +--------------+  +--------------+  +--------------+   │
│    |  🌐 代理节点  |  |  🛠️ 分流配置  |  |  🔍 审计日志  |   │
│    | [香港不限速]  |  |  [模式: 智能] |  |  [环境安全]  |   │
│    +--------------+  +--------------+  +--------------+   │
└───────────────────────────────────────────────────────────┘
```

**采纳的设计**：应用以无边框独立视窗形式存在，Dashboard 首页由"中央能量核 + 三张启动卡片（Proxies / Routing / Audit）"构成，卡片点击后平滑膨胀为全屏舞台。这是一个比"顶部 Tab 导航栏"更有空间感、更贴合"渐进式呈现"哲学的信息架构，予以采纳，替换此前版本中"顶部常驻导航条"的方案。

**⚠️ 优化点 1：展开态之间需要直达切换，避免每次都要退回首页**
原方案里三张卡片展开为全屏后，怎么从"审计日志"直接切到"分流配置"没有说明——如果只能靠"退回首页再点另一张卡片"来回切换，对于经常需要同时对照 Routing 配置和 Audit 日志排查问题的重度用户会很不方便。优化方案：卡片展开为全屏舞台后，控制胶囊左侧追加一个纵向排列的三图标小型切换器（🌐 / 🛠️ / 🔍），允许在展开态之间直接跳转，无需每次回到能量核首页。

**⚠️ 优化点 2：默认窗口尺寸与响应式设计冲突，需统一**
原方案给出默认尺寸 850×600px，但此前版本（7.7 全局交互细节）已确立"桌面端窗口最小宽度锁定在 960px"的响应式规则。两者冲突会导致应用默认启动时就已经处于"挤压变形"的临界状态。**统一调整**：默认窗口尺寸改为 **960×640px**，允许用户拖拽缩放，最小限制 960×600px，与既有响应式断点保持一致。

**⚠️ 优化点 3：macOS 红绿灯自定义存在平台规范风险**
原方案设想给 macOS 红黄绿三色按钮加"全息线型隔离"与紧邻的自定义设置图标。需要注意：Apple 的人机界面指南对紧贴原生红绿灯放置自定义控件、或改造红绿灯视觉样式有明确的不建议倾向，处理不当容易在实际使用中造成误触（拖拽区域判定）或在后续系统更新中出现兼容问题。**建议**：保留 macOS 原生红绿灯的默认样式（不做"全息线型"改造），仅在红绿灯右侧预留 ≥8px 的安全间距后放置设置齿轮图标，视觉上依然统一（同色调、同尺寸），但不触碰原生控件本身。

**⚠️ 优化点 4：Windows 无边框窗口需专门验证 Snap Layout 兼容性**
Tauri 2.0 中设置 `decorations: false` 后，需要自行实现标题栏拖拽区域（`data-tauri-drag-region`）、双击最大化等交互。完全自定义的窗口按钮通常会丢失 Windows 11 的 Snap Layout 悬浮菜单（鼠标悬停最大化按钮弹出的分屏布局选择），这是许多 Windows 用户的高频操作习惯。需要在模块 K 中专门验证 Tauri 是否有对应 API 支持保留这一特性，如果没有，需要在"视觉统一"与"保留原生特性"之间做取舍，并把结论写进《权限预研报告》的姊妹文档。

**保留的设计细节**：设置图标与关闭按钮物理距离 > 60px 的防误触间距设计，予以采纳，写入交互规范。

### 7.2 Dashboard —— 中央能量核

- **视觉呈现**：直径 180px 全息磨砂圆环，环内填充流体动画
- **状态映射**：未连接（静默暗灰 + 呼吸灯）/ 连接中（粒子加速旋转）/ 已连接（全息青渐变流体，**流体波动频率与实时下载网速挂钩**）

**实现要点（新增）**：
- 用 CSS `conic-gradient` 动画或轻量 SVG 方案配合 `requestAnimationFrame` 实现，不引入重型渲染库
- 网速数值直接拿来映射会因瞬时抖动导致动画忽快忽慢，需要做**指数移动平均（EMA）平滑**后再驱动动画参数
- 应用最小化到托盘或窗口不可见时，暂停动画渲染循环，避免后台空耗 CPU/GPU 和电量
- `prefers-reduced-motion` 或软件内性能模式开启时，退化为静态渐变环 + 纯数字展示，不做粒子/流体动画

底部保留最近使用的 3-4 个策略组一键切换胶囊按钮（沿用此前设计）。

### 7.3 Proxies —— 响应式微光网格

- **常态（卡片折叠态）**：地区 Icon + 节点简称 + 延迟小绿点
- **展开态（全屏舞台）**：顶部 `🤖 闪电自动选择` 高亮胶囊，节点按地区分组，大圆角网格布局

**融合既有测速设计（4.2.3）**：
- 节点行右侧保留独立的"⚡延迟"与"📶测速"按钮
- 测速中的进度反馈采用与能量核一致的流体色彩动画（而非普通 loading spinner），保持全局视觉语言统一；测速完成后 Ping/下载/上传数值从小到大滚动闪烁定格，呼应原方案的动效细节
- 批量测速二次确认弹窗同样使用磨砂玻璃卡片风格，不额外引入原生系统弹窗，保证视觉一致性

### 7.4 Routing —— 简单矩阵与拓扑画布的灵魂共生

延续此前"合并 App-Matrix 与拓扑画布，共享同一份出站节点数据源"的决策，本节采纳原方案更精细的交互设计：

**简单模式（App-Matrix）—— 默认激活**：
- 顶部 `🔍 搜索应用、进程...` 输入框 + `🧪 已自定义规则` 筛选胶囊，点击后过滤出已手动修改过规则的进程
- 每行一张独立雾面超椭圆卡片：左侧应用原生高清图标，右侧"出站节点选择胶囊"
- **数据纽带**：下拉菜单中，用户在高级模式搭建好的"多重拓扑链路"以渐变色置顶展示（如 ✨ 游戏加速链）

  > **⚠️ 优化点**：链路和普通单节点在下拉列表中视觉上需要明确区分（如统一加一个链条 🔗 图标前缀，并分组展示），避免用户把"一条多跳链路"误当成"一个普通节点"来选择——链路的连接状态、延迟表现方式与单节点不同，混淆会增加排障难度。

**高级模式（拓扑画布）—— 默认锁定**：
- 默认置灰带锁（🔒 高级模式），悬浮气泡提示"在高级设置中开启拓扑图功能"，点击直达设置项
- 首次解锁进入时，弹出一次性磨砂告知卡片，说明普通单节点用户无需使用此页面
- 空状态渲染全息网络流向插画；建立链路后支持拖拽生成 入口→前置节点→落地VPS→出口 的光效网络轨迹
- 节点支持右键菜单（编辑参数/斩断链路/设为全局出口）；节点过多时自动淡入 Minimap 与无级缩放控制

### 7.5 Audit —— 语义化安全看板

在此前"纯只读监控"的定位基础上，采纳原方案的语义化呈现升级：

- **常态（折叠态）**：全息绿盾牌 + 结论性文案，如"🛡️ 当前网络环境安全，今日已为您加速 1,420 次连接"，为普通用户提供安心感
- **展开态**：把冰冷的抓包规则（如 `match GeoIP(cn) -> direct`）翻译为语义化卡片：
  - `github.com` 🚀 节点加速中（命中海外极客规则）
  - `baidu.com` 🎯 绕过大陆（直接连通）
- **极客后门**：右上角常驻 `🧑‍💻 切换到内核原始日志` 胶囊开关，一键切回传统终端日志流（原始日志同样是只读展示，与"纯只读"的页面定位保持一致）

**⚠️ 优化点 1：统计数字需要真实数据支撑**
"今日已为您加速 1,420 次连接"这类文案如果只是前端摆设的假数字，一旦被细心的用户发现是假的，会严重损害产品的可信度——而 Auroweave 的核心卖点之一恰恰是"绝对透明"。因此要求 Rust 后台新增一个真实的连接计数器模块（`core/connection_counter.rs`），统计口径需在文档中明确定义（如何算作"一次加速连接"），前端展示的数字必须来自这个真实计数器。

**⚠️ 优化点 2：语义化翻译需要兜底方案**
"规则 → 自然语言"的翻译需要维护一张映射表，原方案示例的 GeoIP/直连场景覆盖的是最常见情况。但随着用户自定义规则越来越多，不可能穷举所有场景。需要设计**通用兜底文案**：无法匹配到预设语义模板的规则，仍要展示一条可读的默认信息（如"自定义规则 #3 命中 → 出站:HK-01"），而不是要么完美翻译、要么直接不显示，否则界面会在用户规则变多后逐渐退化回"半成品"状态。

### 7.6 Settings —— 空间形变转场与卡片式分组

**"原位旋出"形变交互**：点击 ⚙️，控制胶囊向左下方几何级放大，主舱雾化退至 Z 轴深处，胶囊边界化为设置面板外壳，原本的 ✕ 按钮在设置态下承接"🔙 返回主舱"职能。

> **⚠️ 优化点：技术复杂度较高，需预研 + 提供降级方案**
> 这个转场本质上是一个跨越"小胶囊"与"全屏面板"两种完全不同尺寸/形态元素之间的共享元素转场（类似 FLIP 动画或 View Transitions API 的典型应用场景）。需要在模块 K 中专门做技术预研 Demo，验证其在 Windows（WebView2/Chromium 内核）与 macOS（WKWebView 内核）上的帧率与视觉一致性表现。**如果预研发现实现成本过高或跨平台表现不一致**，退化为更朴素的"缩放 + 交叉淡入"转场——视觉效果打折扣，但开发成本低得多、兼容性有保障，不建议为了这一处转场效果拖慢整体项目进度。

**卡片式分组视觉（去果味重构）**：全息发光图标（线条图标 + 同色调弱霓虹背光）、截断式渐隐边框、能量注入开关（液体渐变滑入替代传统 iOS 绿色开关）。

> **⚠️ 优化点：装饰性效果需要接入性能模式开关**
> 持续的粒子闪烁背光和霓虹发光对配置较低的机器不友好，也不是所有用户的审美偏好都喜欢这类效果。这类装饰性视觉必须统一接入 `useReducedMotion()`（第 6.2 节新增规范），并在 Settings → 高级设置中提供独立的"性能模式"开关供用户主动选择，与系统级 `prefers-reduced-motion` 联动但不完全依赖它（不能假设所有用户都开着系统级无障碍设置）。

**反向精准锚定定位**：当用户从 Routing 页面点击置灰的"高级模式"跳转到设置时，设置面板中的"🎨 启用拓扑图功能"整行会触发三次流光呼吸高亮，形成防迷路闭环——这是对此前"点击提示可直达设置项"设计的很好的动效补充，予以采纳并写入交互规范。

### 7.7 微交互物理学基础规范

以下三项低成本、高质感的微交互细节，作为全局基础组件库的统一规范写入代码规范（第六章）：

1. **Hover 阻尼反馈**：鼠标滑过可交互元素时，背景色 150ms 内平滑变化 3%
2. **点击阻尼下陷**：点击时 `transform: scale(0.98)`，模拟物理按键的机械阻尼感
3. **窗口边缘高光圈**：无边框窗口外壳包裹一圈 1px、8% 不透明度的白色高光，确保暗色桌面背景下窗口轮廓依然清晰

### 7.8 无障碍与性能兜底（新增）

由于本章融合的视觉方案大幅提升了整体视觉复杂度（毛玻璃模糊、流体动画、粒子背光、FLIP 转场），必须专门补充一节兜底方案，否则容易在低配设备或有无障碍需求的用户群体中翻车：

- **`prefers-reduced-motion` 全面支持**：系统开启该选项时，流体波动降级为静态渐变、粒子背光移除、FLIP 转场降级为淡入淡出，全部动效统一通过 `useReducedMotion()` 判断（见 6.2）
- **软件内独立的"性能模式"开关**：不依赖用户去系统设置里翻找无障碍选项，直接在 Settings → 高级设置中提供一个"性能模式"总开关，一键关闭 `backdrop-filter` 模糊效果（部分老旧集显设备在大面积模糊渲染时掉帧明显）、粒子背光与流体动画
- **高对比度选项**：为视力不便用户提供"减少透明度、提高文字对比度"的独立选项，而非要求用户自行适应磨砂玻璃上略低的对比度文字
- **浅色主题完整 Token 集合**：呼应 7.0 中的优化建议 1，浅色模式必须有独立设计的完整 Token，不能是深色皮肤的简单减淡处理
