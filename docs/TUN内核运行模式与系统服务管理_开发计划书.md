# TUN 内核运行模式与系统服务管理 —— 开发计划书

**所属项目**：Auroweave（Tauri 2.0 + Vue 3 + TypeScript + Sing-box）
**模块定位**：建议归入现有模块体系，作为独立子模块（暂命名 Module TUN-Priv，实际编号由主计划文档统一分配）
**文档版本**：v1.0
**关联背景**：解决 Windows 下 TUN 模式每次启用都需要 UAC 二次确认的问题

---

## 0. 背景与决策依据

此前已完成技术路线讨论，结论如下，作为本计划的设计前提，不再重复展开：

- Windows 创建 TUN 网卡、改路由表需要管理员令牌，普通用户进程默认无法完成
- "整个 App 以管理员身份运行"（Hiddify 早期方案）会破坏开机自启动、多开等体验，予以放弃
- "计划任务静默提权"（Sparkle/Mihomo Party 方案）实现轻量，但常驻性和权限边界不如系统服务清晰，且无法满足"随系统开机自启、脱离用户登录状态运行"的诉求
- 最终选定 **Windows 系统服务（Service）模式**作为核心方案，同时保留**直接运行模式**作为兼容/回退选项，两者可在设置中切换

**关键设计决策（需在评审中确认）**：服务安装的自定义安全描述符（DACL）授予当前登录用户 `SERVICE_START` / `SERVICE_STOP` / `SERVICE_QUERY_STATUS` 权限，但不授予 `SERVICE_CHANGE_CONFIG` / `SERVICE_DELETE`。这样只有"安装/卸载/改配置"这类低频操作需要 UAC 提权，日常的启动/停止服务（对应需求 4、5）GUI 可直接调用，无需二次弹窗。这是本计划能满足需求 4/5 而不引入重复 UAC 的核心前提，务必在实现阶段落实，具体见 §5.4。

## 1. 名词定义

| 术语 | 说明 |
|---|---|
| 直接运行模式（Direct Mode） | GUI 主进程（Rust 后端）直接以自身权限拉起 sing-box 核心子进程。非 TUN 场景下无需提权；若在此模式下请求 TUN，仍会触发原始问题（每次 UAC），本计划不针对此场景做优化，作为历史兼容路径保留 |
| 系统服务模式（Service Mode） | sing-box 核心由独立的 Windows 服务进程托管、启动、停止，GUI 仅通过服务控制接口和本地 IPC 与之交互 |
| 服务宿主二进制 | 新增的独立 Rust 二进制项目，实现 `windows-service` 的服务主体逻辑，同时内部管理 sing-box 子进程 |
| 服务状态 | 未安装 / 已安装-运行中 / 已安装-已停止 / 已安装-异常（如二进制丢失、版本不匹配） |

## 2. 需求拆解与验收标准

### 2.1 设置中新增"内核运行模式"控制项

- 位置：设置页，建议放在现有"内核 / Core"分组下
- 控件：二选一（Segmented Control 或 Radio），选项为 **直接运行** / **系统服务**
- 切换到"系统服务"时，若检测服务未安装，触发 §2.2 的安装询问流程；切换回"直接运行"时，若服务当前处于运行状态，需先安全停止服务（对应 sing-box 核心一并停止），再切换配置，避免出现"配置是直接运行但服务还在跑"的状态不一致
- 验收标准：切换过程中如果用户中途取消/UAC 拒绝，配置项**不落盘**，UI 回退到切换前的状态并给出明确提示

### 2.2 系统服务状态管理面板

- 仅当运行模式选择"系统服务"时展开显示（可用折叠面板承载，避免直接运行模式下的设置页显得杂乱）
- 展示内容：
  - 服务安装状态（未安装 / 已安装且运行中 / 已安装但已停止 / 异常，附状态图标和最近一次错误信息）
  - 服务版本号（与当前 App 内置的服务宿主二进制版本对比，不一致时提示"需要更新服务"）
  - 操作按钮：安装 / 卸载 / 手动启动 / 手动停止 / 查看服务日志
- **未安装时的交互流程**（对应需求 2 的核心逻辑）：

```
用户将运行模式切到"系统服务"
        │
        ▼
  检测服务是否已安装
        │
   ┌────┴────┐
  已安装      未安装
   │            │
   │            ▼
   │      弹窗询问："是否立即安装系统服务？"
   │            │
   │      ┌─────┴─────┐
   │      是            否
   │      │             │
   │      ▼             ▼
   │  触发 UAC 提权   运行模式配置回退为"直接运行"
   │  执行服务安装        UI 提示原因，Toast/提示条说明
   │      │
   │  ┌───┴────┐
   │ 成功      失败/UAC取消
   │  │          │
   │  ▼          ▼
   │ 更新状态   运行模式配置回退为"直接运行"
   │ 为已安装   弹窗告知失败原因（可展开日志）
   ▼
进入正常的已安装状态展示
```

- 验收标准：
  - 弹窗文案需明确告知"这将请求一次管理员权限用于安装后台服务，安装完成后日常使用不会再弹出该提示"，降低用户对突然弹出 UAC 的疑虑
  - 用户选择"否"后，配置**必须**同步回退持久化，而不能只是 UI 显示为直接运行、配置文件里仍是 service，否则会与需求 4 的启动检测逻辑冲突

### 2.3 服务宿主二进制项目

新增独立的 Rust 二进制 crate，专职实现 Windows 服务，详见 §5。

### 2.4 应用启动时的模式检测与自愈

```
App 启动
   │
   ▼
读取配置中的 core.runMode
   │
   ├── direct → 按直接运行逻辑初始化，跳过以下判断
   │
   └── service
         │
         ▼
     查询服务当前状态（SCM 查询，无需提权）
         │
    ┌────┼─────────────┐
   未安装   已安装-已停止   已安装-运行中
    │         │              │
    ▼         ▼              ▼
 回退为    调用 StartService  直接连接服务的
 direct     （relaxed ACL，   本地 IPC，同步
 并提示     无需 UAC）        当前内核状态到
 用户                        GUI 界面
    │         │              │
    │      ┌──┴───┐          │
    │     成功    失败        │
    │      │       │          │
    │      ▼       ▼          │
    │   同上      提示错误，   │
    │  运行中     回退为        │
    │            direct 并     │
    │            记录日志       │
    ▼──────────────────────────▼
              GUI 主界面完成初始化
```

- 验收标准：任何"回退为 direct"的分支都必须写日志（含原因：未安装 / 启动失败 / 服务无响应），便于用户反馈问题时定位

### 2.5 应用关闭 / 点击"关闭代理"按钮时的服务同步

- 两个触发点行为一致：若当前为服务模式，则调用 `ControlService(SERVICE_CONTROL_STOP)` 停止服务（服务内部收到 Stop 信号后，先优雅终止 sing-box 子进程，再从服务主函数返回，SCM 随之将服务状态置为 Stopped）
- "点击关闭代理"与"退出整个 App"的区别仅在于：前者停止服务后 GUI 主进程仍在运行（用户可以随时再次启动），后者停止服务后 GUI 主进程也退出
- 需要处理的边界：
  - 停止服务的调用本身有一定耗时（sing-box 优雅退出 + 网卡销毁），GUI 侧需要有超时机制（建议 5-8 秒），超时后允许用户强制退出 App，但要提示"服务可能仍在后台运行"，并在下次启动时重新做状态检测和自愈（对应 §2.4）
  - App 异常崩溃（未走到正常退出流程）导致服务未被停止：属于预期情况，不需要特殊处理，因为服务本来就设计为可以独立于 GUI 存在，下次 GUI 启动时会检测到"已安装-运行中"并直接接管

## 3. 架构总览

```
┌──────────────────────────────┐
│   Tauri GUI 主进程（用户权限） │
│   Vue3 前端 ←→ Rust 后端       │
└───────────────┬───────────────┘
                 │
     ┌───────────┴────────────┐
     │                        │
 direct 模式               service 模式
     │                        │
     ▼                        ▼
直接 spawn 子进程      ① SCM 控制接口（Start/Stop/Query，relaxed ACL，免UAC）
sing-box.exe（用户      ② 本地具名管道 IPC（配置下发/状态查询/日志流）
权限，无 TUN 能力）              │
                                ▼
                    ┌────────────────────────┐
                    │  auroweave-svc.exe      │
                    │  Windows 服务宿主进程    │
                    │（SYSTEM 权限，常驻）      │
                    │  内部管理 sing-box 子进程 │
                    └────────────────────────┘
```

**关键原则**：GUI 不直接管理服务模式下的 sing-box 进程，所有操作（启用/禁用 TUN、切换配置、重启内核）都通过 IPC 下发给服务宿主进程，由它代为执行。GUI 与服务的关系类似"遥控器和电视"，而不是"两个各自独立的进程"。

## 4. 配置层设计

### 4.1 配置字段变更（settings schema）

```jsonc
{
  "core": {
    "runMode": "direct" | "service",   // 新增
    "service": {                        // 新增，仅 service 模式下有意义
      "installedVersion": "1.2.0",      // 记录已安装的服务宿主版本，用于升级检测
      "lastKnownStatus": "running" | "stopped" | "not_installed" | "error",
      "lastFallbackReason": null | "not_installed" | "start_failed" | "uac_denied" | "timeout"
    }
  }
}
```

- `lastFallbackReason` 用于 §2.4 中"自动回退"场景的用户提示与问题排查，不参与实际逻辑判断（实际判断以实时查询 SCM 状态为准，避免配置文件里的缓存状态与系统实际状态不一致导致误判）
- **原则：任何"当前服务是否安装/运行"的判断都必须实时查询 SCM，配置文件中的字段只做展示和日志用途，不作为决策依据**，防止因为配置文件与系统实际状态脱节导致的连锁错误

## 5. 服务宿主二进制项目设计

### 5.1 Cargo workspace 结构调整

```
auroweave/
├── src-tauri/                  # 现有 Tauri 主程序
│   ├── src/
│   └── Cargo.toml
├── crates/
│   └── auroweave-svc/          # 新增：服务宿主二进制
│       ├── src/
│       │   ├── main.rs         # 服务入口 + 命令行子命令分发
│       │   ├── service.rs      # windows-service 服务主体
│       │   ├── core_manager.rs # sing-box 子进程生命周期管理
│       │   ├── ipc.rs          # 具名管道 server 端
│       │   └── installer.rs    # install/uninstall 子命令实现
│       └── Cargo.toml
└── Cargo.toml                  # workspace 根
```

- `auroweave-svc` 与 `sing-box` 核心解耦，不重复实现规则解析等逻辑；它只负责"以正确权限拉起/管理 sing-box 进程 + 对外暴露控制接口"
- 支持命令行子命令：`auroweave-svc.exe install` / `uninstall` / `run`（作为服务主体被 SCM 拉起时使用），便于统一二进制、简化打包

### 5.2 打包与部署

- 在 `tauri.conf.json` 的 `bundle.resources` 中声明 `auroweave-svc.exe`，随安装包一起分发到安装目录（如 `%ProgramFiles%\Auroweave\auroweave-svc.exe`）
- **不要**使用 Tauri 的 `externalBin`/sidecar 机制来启动它——sidecar 适合"GUI 直接管理的子进程"，而服务的生命周期要脱离 GUI 独立存在，需要走标准 SCM 注册流程，两者语义不同，混用容易导致服务安装路径解析、更新替换逻辑复杂化
- 安装路径固定在 Program Files 下，普通用户无写权限，防止服务对应的可执行文件被替换后造成本地提权（对应 §7.2 安全设计）

### 5.3 服务主体逻辑（`service.rs`）

- 基于 `windows-service` crate 实现标准的 `SERVICE_MAIN` 入口
- 服务的 **启动类型建议设置为 Manual（Demand Start）**，而非 Auto：因为是否需要"开机自动拉起服务"应由 GUI 的自启动逻辑决定（如果 GUI 配置了随开机启动+服务模式，由 GUI 首次运行时调用 StartService 来触发，而不是让服务自己在开机时无条件启动，这样能保持"服务是否运行"与"用户是否需要代理"语义一致，避免用户没打开 GUI 时后台也在跑代理）
- 状态转换需正确响应 `SERVICE_CONTROL_STOP` / `SERVICE_CONTROL_INTERROGATE`，收到 Stop 信号后：
  1. 立即上报 `SERVICE_STOP_PENDING`（并给出合理的 `dwWaitHint`，避免 SCM 认为服务卡死）
  2. 通知 `core_manager` 优雅终止 sing-box 子进程（先尝试正常关闭 TUN 网卡、清理路由表，超时后强制 kill）
  3. 关闭 IPC 管道监听
  4. 上报 `SERVICE_STOPPED`，服务主函数返回

### 5.4 服务安装与 ACL 设计（关键）

安装（`install` 子命令）需要在提权环境下执行，步骤：

1. 调用 `CreateService`，`dwStartType = SERVICE_DEMAND_START`
2. 安装完成后，立即调用 `SetServiceObjectSecurity` 设置自定义 DACL，参考 SDDL：

```
D:(A;;CCLCSWRPWPDTLOCRRC;;;SY)(A;;CCDCLCSWRPWPDTLOCRSDRCWDWO;;;BA)(A;;CCLCSWLOCRRC;;;AU)
```

   - `SY`（SYSTEM）、`BA`（Administrators）：完全控制
   - `AU`（Authenticated Users）：仅授予 `CC`（QueryConfig）、`LC`（QueryStatus）、`SW`（Start）、`LO`（Stop 对应位）、`RC`（ReadControl），**不含** `WP`（ChangeConfig）与 `DT`/`SD` 相关的删除权限
3. **触发方式**：GUI 侧不直接调用 Win32 API，而是通过 `ShellExecuteW` 以 `"runas"` 动词拉起 `auroweave-svc.exe install`，让系统弹出标准 UAC 对话框；安装子命令执行完毕后返回退出码，GUI 通过等待子进程结束 + 读取退出码判断成功与否
4. 卸载（`uninstall`）同理需要提权，走相同的 ShellExecute + runas 方式

**日常的启动/停止（对应需求 4、5）**：由于 ACL 已经放开给 Authenticated Users，GUI 直接调用 `OpenSCManager` → `OpenService` → `StartService`/`ControlService` 即可，全程无 UAC。

### 5.5 IPC 协议（GUI ↔ 服务）

- 传输：Windows 具名管道（`\\.\pipe\Auroweave.Core.Control`），Rust 侧用 `tokio::net::windows::named_pipe`
- 鉴权：管道创建时设置 ACL 仅允许当前交互式用户会话访问；同时消息体内附带一个安装时生成、存放在受保护目录下的本地 token，双重校验，防止同机其他低权限进程伪造指令（这是本地提权类软件的常见攻击面，务必落实，不能仅依赖管道 ACL）
- 协议内容（JSON，简化版）：
  - `GET_STATUS` → 返回内核运行状态、TUN 是否启用、当前进程 PID 等
  - `SET_TUN(enabled: bool)`
  - `RELOAD_CONFIG(config: SingBoxConfig)`
  - `SHUTDOWN_CORE`（仅终止内核子进程，服务本身继续运行，用于"重启内核"这类场景，与 §2.5 的"停止服务"是两个不同粒度的操作，实现时注意不要混淆）

## 7. 其他细节完善

### 7.1 版本升级与服务二进制不一致处理

- App 升级后，`auroweave-svc.exe` 可能也随之更新，但已安装的 Windows 服务在系统层面仍指向旧文件路径，文件被安装程序原地覆盖后：
  - 若服务当前未运行：下次 GUI 检测到版本号不一致（对比 §4.1 中 `installedVersion` 与新版本内置的服务版本），提示用户"服务需要更新"，走一次"卸载旧服务 → 安装新服务"的流程（会有一次 UAC，属于合理的低频操作）
  - 若服务当前正在运行：不能直接覆盖正在被占用的可执行文件（Windows 文件锁定），安装程序需要在覆盖前先停止服务（用普通启停权限即可），覆盖后视配置决定是否重新拉起

### 7.2 安全设计小结

- 服务可执行文件路径固定在受保护目录（Program Files），普通用户不可写，防止被替换为恶意程序后借助已放开的 Start 权限实现本地提权
- IPC 管道需要管道 ACL + 应用层 token 双重校验（§5.5）
- 服务 DACL 严格限制为"仅可查询状态、启停"，任何配置变更/卸载/删除类操作都必须走 UAC 提权路径，不放给普通用户权限

### 7.3 异常与容灾

| 场景 | 处理方式 |
|---|---|
| 服务安装后从未启动过用户就直接改了 direct 模式 | 属正常场景，无需清理服务，下次切回 service 模式时直接复用已安装的服务 |
| 用户通过系统"服务"管理器手动删除/禁用了服务 | GUI 下次检测状态时会发现"未安装"或"已禁用无法启动"，走 §2.4 的回退流程，并在设置面板中给出明显提示 |
| sing-box 子进程在服务内部异常崩溃 | `core_manager` 检测到子进程退出，通过 IPC 主动推送状态变更事件给 GUI（而非等 GUI 轮询），GUI 展示"内核异常退出"，提供一键重启（复用 `RELOAD_CONFIG`/重新拉起子进程，不需要重启整个服务） |
| 多用户会话同时使用（同一台机器多个系统账户） | Windows 服务是系统级单实例，不为每个用户会话单独运行；本期不考虑多用户并发场景，仅支持单一活跃会话使用 service 模式，需在文档/UI 中注明限制 |
| 卸载整个 App | 安装程序（NSIS/WiX）卸载流程中需要调用 `auroweave-svc.exe uninstall`（提权），彻底移除服务注册项，避免残留 |

### 7.4 日志设计

- 服务侧日志建议落盘到独立目录（如 `%ProgramData%\Auroweave\service.log`），因为服务以 SYSTEM 权限运行，不适合写入用户 AppData 目录
- GUI 侧"服务状态管理"面板提供"查看服务日志"入口，读取上述日志文件展示（只读展示即可，不需要额外权限）

## 9. 测试计划要点

- **状态矩阵测试**：覆盖"配置为 direct/service × 服务实际为未安装/已停止/运行中/异常"的全部组合，验证启动检测逻辑（§2.4）是否都能落在预期分支
- **UAC 交互测试**：安装/卸载过程中在 UAC 弹窗阶段主动点击"否"，验证配置回退是否正确、是否有残留的中间状态
- **权限边界测试**：以受限用户账户（非管理员组）验证是否仍能正常启停已安装的服务（应当可以，因为 ACL 已放开 Start/Stop 给 Authenticated Users），但无法安装/卸载/改配置（应当被拒绝）
- **异常恢复测试**：手动在任务管理器中 kill 掉服务内的 sing-box 子进程，验证 GUI 是否能收到状态推送并正确展示"异常退出+可重启"
- **升级测试**：模拟服务运行中触发 App 升级，验证文件覆盖与服务重装流程是否会导致代理长时间中断或残留旧服务注册项
